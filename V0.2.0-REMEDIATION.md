# Governance Canon v0.2.0 remediation record

This candidate preserves the v0.1.0 tag and its result files unchanged. It
adds a write-once result path, path canonicalization, kernel-issued concept
registration, and exact receipt subject/version binding.

## Measured candidate checks

- Canon SHA256SUMS: 3/3 unchanged and valid.
- EXP-001 candidate run: 1/8 permitted, preserving the preregistered finding.
- EXP-002 candidate run: 0/8 regression permits, 0/4 remedy-surface deviations;
  probe K remains an observed execution as preregistered.
- EXP-003 candidate run: 0/12 regression permits, 0/10 class deviations,
  0/5 availability refusals, and 0 errors. New probes T (write traversal), U
  (receipt subject mismatch), V (stale receipt version), W (read traversal),
  and X (unsafe read syntax), plus Y (scratch-prefix sibling), all refused.

- `verify_reproducibility.py` checks recorded source digests against the current
  tree and compares every semantic endpoint and probe-record field, normalizing
  only run-specific nonce text.

The canonical EXP-003 result is `RESULT-v0.2.0-final.json`; intermediate local
reruns are not release artifacts. Existing `RESULT.json` files are never
overwritten. The candidate remains a reference-model experiment: it does
not establish production enforcement, cryptographic receipt authenticity, or
external verification of the frameworks.

## Remaining boundary

Receipt issuer strings and digests remain non-authenticating reference values;
cryptographic issuer keys are outside this candidate. The path model rejects
ambiguous relative syntax for both reads and writes, but a production executor
still needs an OS-level symlink and filesystem policy. Derivation precedence is
explicit (outside-boundary effects are stricter than durable in-scope writes),
but a permutation test remains follow-up work. These are explicit limitations,
not silently claimed as solved here.
